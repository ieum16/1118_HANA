## 3. 두 번째 작업: 연락처 백업·복원

### 추천 범위

- 연락처를 버전 정보가 있는 JSON으로 내려받기.
- 파일 선택 → 형식 검증 → 추가·갱신·충돌 건수 미리보기 → 적용 또는 취소.
- 기본은 기존 자료에 병합. 전체 교체는 별도 선택과 확인 후 처리.
- 업체명 + 담당자명 정규화와 기존 중복 규칙을 재사용한다.
- 같은 이름의 중복 후보가 여러 개면 임의로 덮어쓰지 않는다.
- 잘못된 파일이나 취소 시 기존 데이터는 그대로 유지한다.
- 실제 연락처 백업 파일은 GitHub에 커밋하지 않는다.

완료 기준: 가짜 연락처를 내보내 다른 브라우저에서 복원하고, 재가져오기 때 중복이 늘지 않으며 수정된 연락처 처리와 취소를 확인한다.
prd.md·test.md·README.md도 함께 갱신한다.

## 4. 세 번째 작업: 반복 조치 템플릿

연락처 관리와 함께 실제 문의 대응 시간을 줄이는 기능이다.

- 문의 유형·템플릿 이름·안내 제목·조치 순서·추가 안내를 저장한다.
- 저장한 템플릿 선택으로 입력을 채우고, 새로 저장·수정·삭제한다.
- 연락처는 최신 목록에서 선택한다. 템플릿에 오래된 전화번호를 고정하지 않는다.
- 작성 중 내용이 있을 때 다른 템플릿으로 바꾸면 확인한다.
- 연락처와 함께 백업할지, 별도 백업할지 정하고 파일 형식 버전을 관리한다.

완료 기준: 같은 문의에서 저장 템플릿을 불러와 최소 수정 후 복사할 수 있고 새로고침 후에도 템플릿이 유지된다.

## 5. DT 포털은 그다음 무엇을 할까

직원 모두에게 장애를 보이게 하려는 목적에 비해, 현재 **장애·인프라·계약이 브라우저에만 저장**되는 간극이 크다.
제안 공유가 된다고 다른 데이터도 공유되는 것은 아니다.

권장 순서:

1. 공통 장애 공지부터 여러 PC에서 조회·갱신되도록 서버 저장 범위를 설계한다.
2. 실제 계정 인증과 서버 권한 검사를 정한다. 역할 선택 드롭다운만으로 변경 권한을 보호할 수는 없다.
3. DT만 공지 작성·복구 처리, 직원은 조회할 수 있게 서버에서도 검사한다.
4. 이어서 인프라·계약의 공유 저장, 변경 이력, 충돌 처리, 백업 복원을 다룬다.
5. 자동화 제안에는 입력 제한·등록 남용 대응 등 실제 운영에 필요한 보완을 검토한다.
6. ‘프로그램 운영’의 실제 업무 항목이 정해지면 그때 화면을 구체화한다.

완료 기준: 서로 다른 PC에서 같은 장애를 보고, 권한 없는 계정의 변경 요청은 서버에서 거절되며, 새로고침 후 상태가 유지된다.
현재 공개 시안에서 실제 장비·계약 정보를 먼저 넣는 방식으로 진행하지 않는다.
