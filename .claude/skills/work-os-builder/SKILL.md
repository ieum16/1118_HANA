# 나만의 업무 OS 만들기 (웹페이지형)

**업무 OS** = 매일 아침 브라우저에서 여는 한 장짜리 페이지. 내가 반복하는 일을 한곳에 모아서 덜 찾고, 덜 베끼고, 덜 까먹게 해 준다.

## 결과물 (순서대로)

| # | 파일 | 내용 |
|---|---|---|
| 1 | `os-prd.md` | 업무 OS 기획서 (현업 PRD 형식) |
| 2 | `os-build-plan.md` | 제작 계획서 |
| 3 | `index.html` | **"만들까요?"에 그렇다고 한 뒤에만** 만든다 |

**1118_HANA 수업 저장소 안이면** `실습3_나만의도구/<닉네임>/` 에 둡니다 (AGENTS.md 규칙이 우선). 그 밖의 곳에서는 폴더는 `my-os/`를 쓰고, 이미 있으면 `<닉네임>-os/`를 쓴다. 덮어쓰기 전에는 묻는다.

## 먼저 · 두 가지 모드 중 고르기

첫 질문 전에 이렇게 묻는다. 수업 저장소(1118_HANA)의 실습3이면 ①을 추천한다.

> 어떤 걸 만들고 싶으세요?
> ① **작은 도구** — 한 가지 일을 하는 계산기 · 작성기 · 점검표 (실습3 추천)
> ② **업무 OS** — 매일 아침 여는 업무 화면 (할 일 · 기록 표 · 문구 모음을 한 장에)

- ②를 고르면 아래 1~6단계를 그대로 따른다.
- ①을 고르면 바로 아래 **작은 도구 모드**를 따른다.
- 사용자가 처음부터 계산기 · 작성기 · 점검표처럼 작은 도구를 말했으면 묻지 않고 ①로 간다.
- `00_자기소개/<닉네임>.md`가 있으면 하는 업무를 먼저 읽는다. 그러면 "어떤 일을 하세요?"는 "○○ 업무를 하신다고 적어 주셨네요. 맞나요?"로 바꿔 묻는다.

## 작은 도구 모드 (실습3 · 교안 실습 ⑪~⑫)

결과물은 **`prd.md` → (만들까요?) → `index.html` + `test.md`** 세 개다. `os-prd.md` · `os-build-plan.md`는 만들지 않는다. 완성 예시는 저장소의 `[강사예시]/실습3_나만의도구/예적금-만기계산기/`에 있다.

> **결과물은 반드시 HTML 하나(`index.html`)다.** 브라우저에서 더블클릭으로 열리고, 서버 · 로그인 · 설치 · API 키 · 실제 데이터 없이 돌아가야 한다. 엑셀 파일 · 메신저 봇 · 자동 메일 발송 · 사내 시스템 연동처럼 HTML 하나로 안 되는 아이디어는 **HTML로 되는 모양으로 바꿔서** 제안한다 (예: 자동 발송 → 문장을 만들어 복사 버튼, 엑셀 합치기 → 표를 붙여 넣으면 정리해 주는 화면, 시스템 조회 → 화면에서 복사해 붙여 넣기). 바꿀 수 없으면 "다음 단계(서버 · 보안 승인 필요)"로 남긴다.

수강생에게 칸을 채우게 하지 않는다. **불편을 들으면 Codex가 먼저 해결 아이디어를 내고**, 수강생은 고르고 고치기만 한다. 이 모드에서는 질문을 **한 번에 하나씩** 한다 (아래 "대화 원칙"의 라운드당 2~3개는 업무 OS 모드 기준).

1. **불편 듣기 (질문 한 번에 하나씩, 예시 답을 함께).**
   - "어떤 일을 하세요? 하루에 실제로 하는 일로요." (회사 이름 · 고객 정보는 빼고)
   - "업무에서 가장 반복되고 불편한 건 무엇인가요? 얼마나 자주, 지금은 무엇으로 하세요?" 막히면 `references/tool-ideas.md`의 직군별 불편 예시를 2~3개 보여 주고 고르게 한다.
   - 듣고 나면 가설로 되짚는다: "들어 보니 진짜 비용은 *계산보다 옮겨 적기* 같은데, 맞나요?"
2. **해결 아이디어 2~3개 제안 ⭐** — 불편을 한 문장으로 정리한 뒤, 그 불편을 줄이는 **HTML 도구** 아이디어를 카드로 낸다. `references/tool-ideas.md`의 유형(계산기 · 작성기 · 점검표 · 변환기 · 현황판)에서 고르고, 직무에 맞게 이름을 짓는다.
   ```
   😮‍💨 불편: "[언제] [무슨 일]을 [얼마나 자주] 하는데, [어느 부분]이 번거롭다"

   💡 이렇게 풀 수 있어요 (모두 index.html 한 장)
   ① [도구 이름] — [무엇을 넣으면] → [무엇이 나온다] · 줄어드는 일: [___] · 난이도: 쉬움
   ② ...
   ③ ...
   추천은 ①이에요. 처음 만들기에 실패가 가장 적어요. 어떤 걸로 할까요? (섞어도 돼요)
   ```
   아이디어마다 **지금 방식과 무엇이 달라지는지** 한 줄(예: "계산기 두드리고 다시 적기 → 숫자 넣으면 안내 문장까지 복사")을 붙인다. 쉬운 것부터 순서대로 놓는다.
3. **PRD 초안을 Codex가 채워서 보여 주기** — 고른 아이디어로 누가 쓰나 · 입력 · 출력 · 꼭 필요한 기능(**3개 이하**) · 있으면 좋은 기능 · 예외 상황을 Codex가 먼저 채워 짧게 보여 주고 "고칠 곳 있나요?"만 묻는다. 꼭 필요한 기능이 4개 이상이면 3개만 남기고 나머지는 있으면 좋은 기능으로 옮기자고 제안한다.
4. **`prd.md`** — 한 줄 소개 · 누가 쓰나 · 줄이고 싶은 불편 · 입력 · 출력 · 꼭 필요한 기능(3개) · 있으면 좋은 기능 · 예외 상황 · 조건(HTML 파일 하나, 로그인 없음, 가짜 데이터). 안 나온 칸은 합리적으로 채우고 `(가정)`을 단다.
5. **"만들까요?"** — prd.md 경로와 핵심(입력 · 출력 · 꼭 필요한 기능 3개)만 짧게 보여 주고 **반드시 멈추고** 묻는다. 1. 지금 만들기 2. 기능 바꾸고 만들기 3. 기획 고치기
6. **`index.html`** — 꼭 필요한 기능 3개만 먼저 만든다. 파일 하나, CSS · JS는 안에, 로그인 · 서버 없음, 더블클릭으로 열림. 처음 열었을 때 **가짜 예시 값**이 들어 있어 결과가 바로 보이게 한다. 빈칸 · 0 · 음수 · 글자 같은 잘못된 입력에는 쉬운 안내 문구를 띄운다. 금액 · 세금처럼 실제와 다를 수 있는 숫자가 있으면 "실제 값은 회사 시스템 기준" 안내를 화면 아래에 단다. 입력 내용을 바깥으로 보내지 않는다. 다시 열 때 남아 있으면 편한 칸(담당자 이름 등)만 `localStorage`에 저장해도 된다(`try/catch`로 감싸기). 색은 사용자가 말하지 않았으면 차분한 남색 계열로 하고 그렇다고 말한다.
   다 만들면 **직접 확인한다.** 미리보기가 되면 열어서 예시 결과가 바로 보이는지, 375px 폭에서 가로 스크롤이 없는지, test.md 항목 2~3개를 해 본다. 미리보기가 안 되면 `index.html`을 더블클릭해서 확인해 달라고 안내한다. 확인하지 못한 것은 못 했다고 말한다.
7. **`test.md`** — prd.md 기준 테스트 체크리스트. `꼭 필요한 기능` · `예외 상황` · `있으면 좋은 기능` 세 표로 나누고, 칸은 `번호 | 해 볼 것 | 기대 결과 | ○/×`. 기대 결과에는 실제로 나와야 할 값을 적는다.
8. **마무리** — "test.md대로 눌러 보고 ×가 나오면 3줄 공식(무엇을 했더니 · 기대한 것 · 실제 결과)으로 말해 주세요"라고 안내하고, 있으면 좋은 기능 1개를 붙여 보자고 제안한다. 제출은 AGENTS.md의 "실습3 올려 줘" 대본을 따른다.

## 대화 원칙

- **한 번에 한 라운드**, 질문은 2~3개, 예시 답을 함께 준다.
- 답을 들으면 **가설을 던져 확인**한다: "들어 보니 진짜 비용은 ___ 같은데, 맞나요?" 사용자가 스스로 몰랐던 핵심을 찾게 하는 것이 이 스킬의 가치다.
- 막히면 비슷한 직무의 예시를 2~3개 보여 주고 고르게 한다.
- **처음 버전은 작게.** 화면 모듈은 최대 3개. 나머지는 "다음에 붙일 것"으로 남긴다.
- 개인정보 · 회사 정보는 넣지 않는다. 실명 대신 닉네임, 회사 이름 · 고객 정보 · 사내 시스템 주소 · 비밀번호 · API 키는 쓰지 않는다. 화면에 들어갈 예시 데이터는 가짜로 만든다.

## 1단계 · 인터뷰 (4라운드)

질문 원문과 예시 답은 `references/question-bank.md`에 있다.

1. **일의 풍경** — 어떤 일을 하는지, 하루·한 주에 시간을 가장 많이 쓰는 일 3가지
2. **반복과 불편** ⭐ — "업무에서 가장 반복되고 불편한 건 무엇인가요?" 얼마나 자주, 몇 분, 지금은 어떤 도구로 하는지. 어느 부분이 진짜 비용인지 한 번 더 파고든다.
3. **이상적인 아침** — "출근해서 이 페이지를 열면 무엇이 이미 보이면 좋겠어요?"
4. **기록할 것** — 무엇을 적고 관리하는지(항목·칸), 혼자 쓰는지 팀이 쓰는지, 휴대폰에서도 보는지

라운드 2가 끝나면 통점을 한 문장으로 되짚는다.

```
🎯 내 업무 OS가 풀 문제
"나는 [언제] [무슨 일]을 [얼마나 자주] 하는데, [어느 부분]이 가장 번거롭다."
```

`references/module-catalog.md`에서 통점에 맞는 모듈을 **2~3개 추천**하고 이유를 한 줄씩 붙인다. 사용자가 고르게 한다. 그리고 화면 배치를 글 그림으로 보여 준다.

```
┌──────────── 오늘 · 11월 6일 (목) ────────────┐
│ [모듈 A: 오늘 할 일]   │ [모듈 B: 숫자 요약]  │
├────────────────────────┴─────────────────────┤
│ [모듈 C: 기록 표]                             │
└───────────────────────────────────────────────┘
```

`templates/os-prd-template.md`를 따른다. 인터뷰에서 안 나온 칸은 합리적으로 채우고 `(가정)`을 단다. 데이터 칸(필드) 표를 꼭 채운다. 만들 때 이 표가 그대로 쓰인다.

## 4단계 · 제작 계획서 → `os-build-plan.md`

`templates/os-build-plan-template.md`를 따른다. 모듈별 구현 순서, 데이터 저장 방식, 확인 방법을 적는다.

## 5단계 · "만들까요?"

두 파일 경로를 알려 주고 **반드시 멈추고** 묻는다.

> 기획서와 계획서가 나왔어요. 이대로 업무 OS를 만들까요?
> 1. 지금 만들기
> 2. 모듈 바꾸고 만들기 — 빼거나 더할 모듈을 말해 주세요
> 3. 기획 고치기

## 6단계 · 만들기 → `index.html`

만드는 규칙:
- **파일 하나**(`index.html`), CSS · JS 모두 안에 넣는다. 빌드 도구 · 서버 · 로그인 없음. 더블클릭으로 열린다.
- **저장은 브라우저 `localStorage`**. 키 이름은 `myos:<모듈>` 형식. 읽고 쓸 때 `try/catch`로 감싸서 저장이 막혀도 화면은 뜨게 한다.
- **백업 · 복원 버튼**: 전체 데이터를 JSON 파일로 내려받기 / 파일에서 불러오기. 브라우저 기록을 지우면 데이터가 사라질 수 있다고 화면과 안내에 적는다.
- 처음 열었을 때 비어 있지 않게 **가짜 예시 데이터 3~5건**을 넣고, "예시 지우기" 버튼을 둔다.
- 맨 위에 오늘 날짜와 인사, 그 아래 고른 모듈. 데스크톱 2열 → 휴대폰 1열. 휴대폰 좌우 여백 16px, 가로 스크롤 없음.
- 색은 `:root` 변수로 모은다. 사용자가 분위기를 말하지 않았으면 차분한 남색 계열로 하고 그렇다고 말한다.
- 외부 서비스로 데이터를 보내지 않는다.

다 만들면 확인한다.
- 미리보기가 되면: 항목 추가 → 새로고침 → 그대로 남는지, 백업 파일이 받아지는지, 375px 폭에서 깨지지 않는지 본다.
- 미리보기가 안 되면: `index.html`을 더블클릭해서 위 세 가지를 직접 해 보라고 안내한다.

## 마무리 안내

- 만든 파일과 쓰는 법 3줄 (열기 → 입력 → 백업)
- 브라우저 즐겨찾기에 추가하거나 시작 페이지로 두라고 권한다.
- 다음에 붙일 것 1~2개를 문장으로 제안: "주간 요약 칸을 추가해 줘", "자주 쓰는 문구 복사 칸을 넣어 줘"
- 이 OS를 팀과 같이 쓰고 싶다면 그건 서버나 공유 저장소가 필요한 다음 단계라고 알려 준다.
